## B1 — Rate limiting для endpoint-ов аутентификации

**Проблема.** Lockout в ASP.NET Core Identity настроен корректно (5 неудачных
попыток, 15 минут), но защищает только один аккаунт. Ничто не ограничивает
распределённый перебор паролей по множеству аккаунтов, а у форм входа и
регистрации нет ограничения частоты запросов. Ревью отметило
`POST /api/v1/auth/login` и поток регистрации.

**План.**
- Подключить встроенный rate limiter ASP.NET Core
  (`builder.Services.AddRateLimiter`) со скользящим или фиксированным окном,
  партиционированным по IP клиента.
- Применить более строгую политику к `POST /api/v1/auth/login` (например,
  5 попыток в минуту на IP) и к POST-формам входа/регистрации Blazor.
- Возвращать `429 Too Many Requests` с `Retry-After`; lockout оставить
  защитой на уровне аккаунта.
- Читать IP клиента из `ForwardedHeaders`/`X-Forwarded-For` только когда
  приложение стоит за доверенным прокси, и описать настройку прокси в доке.

**Критерии приёмки.**
- Повторные попытки входа с одного IP получают `429` после заданного лимита.
- Успешный вход с другого IP по-прежнему возможен.
- Значения лимитов берутся из конфигурации, а не из кода.
- Integration-тесты покрывают путь `429` и заголовок.

**Примечания.** Лимиты должны быть достаточно мягкими, чтобы обычные
пользователи за общим NAT не попадали под ограничение; перед ужесточением
проверить значения на целевой площадке деплоя.

## B2 — Изоляция E2E-тестов от общего демо-состояния

**Проблема.** `UserJourneyTests` использует одного засеянного демо-пользователя
(`demo@todolist.local`) и делит его задачи между тестами. Поэтому набор зависит
от порядка выполнения и не может безопасно распараллеливаться.

**План.**
- Дать каждому тесту своего пользователя: регистрировать уникальный аккаунт
  через существующий поток регистрации (или небольшой API/helper) с
  `Guid`-суффиксом в email.
- Засеивать только те данные, которые нужны тесту; не зависеть от демо-задач.
- Оставить демо-аккаунт для ручной оценки, а не для автоматических проверок.
- Если регистрация через UI слишком медленная, добавить тестовый endpoint под
  `IsEnvironment("Testing")`/`IsDevelopment()`.

**Критерии приёмки.**
- Каждый E2E-тест создаёт и владеет своим пользователем и данными.
- Тесты проходят в любом порядке и при включённом распараллеливании xUnit
  внутри коллекции.
- Ни один тест не проверяет данные, созданные другим тестом.

## B3 — Детерминированное время в тестах напоминаний

**Проблема.** Integration-тесты напоминаний используют `TimeProvider.System` и
считают `scheduledAtUtc` через `DateTimeOffset.UtcNow.AddMinutes(...)`. На
медленном CI-агенте напоминание может стать due раньше, чем ожидает проверка,
из-за чего тесты чувствительны к таймингам и иногда флакают.

**План.**
- Вернуть `Microsoft.Extensions.TimeProvider.Testing` в
  `Directory.Packages.props` и регистрировать `FakeTimeProvider` в
  integration-хосте для тестов напоминаний.
- Двигать время явно (`provider.Advance(...)`), а не добавлять реальные
  смещения; проверять точные значения `ScheduledAtUtc`.
- По желанию вынести общий helper `FakeTimeProvider` в `TodoList.Testing`,
  чтобы unit- и integration-тесты использовали один подход.

**Критерии приёмки.**
- Ни один тест напоминаний не зависит от реальных задержек.
- Расписание back-off проверяется точно (1, 2, 4, 8 минут, ограничение 60).
- Тесты остаются зелёными под нагрузкой на машине.

## B4 — Зафиксировать решение об общей БД для integration-тестов

**Проблема.** Все integration-тесты одной коллекции используют одну базу
Testcontainers PostgreSQL. Данные между тестами не сбрасываются; уникальные
email не дают им столкнуться, но строки накапливаются линейно, а некоторым
тестам нужна ручная очистка (например, ожидающие напоминания). Ревью сочло это
приемлемым для MVP, но попросило зафиксировать как осознанное решение, а не
случайность.

**План.**
- Описать компромисс в `docs/development/testing.ru.md` (и английской паре):
  один контейнер на коллекцию, без сброса на каждый тест, уникальные
  идентификаторы, точечная очистка там, где важен порядок.
- Сослаться на решение из ADR 0005, чтобы будущие участники знали, что это
  намеренно.
- Зафиксировать момент пересмотра: когда набор станет медленным или тесту
  понадобится изоляция между тестами, перейти на транзакцию/схему на тест или
  сброс в стиле Respawn.

**Критерии приёмки.**
- Гайд по тестированию и ADR описывают текущий подход и его ограничения.
- В заметке указан триггер пересмотра решения.

## Вне scope

- Нагрузочное и производительное тестирование под реальным трафиком.
- Поведение доставки с реальным SMTP-провайдером (Mailpit покрывает happy
  path; продовый SMTP проверяется при деплое).
- Измерение покрытия; ревью делало выводы о пробелах по чтению тестов.
