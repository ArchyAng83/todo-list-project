# Стратегия тестирования

## Пирамида

| Уровень | Инструменты | Что покрывает | Когда |
|---|---|---|---|
| Unit | xUnit, Shouldly, NSubstitute | Доменные правила, валидация, расчёты часовых поясов, чистая логика Application | Каждый коммит |
| Integration | WebApplicationFactory, Testcontainers PostgreSQL | EF Core mappings/migrations, Application-сервисы, Identity, API, изоляция данных, конкурентность | Каждый PR |
| Component | bUnit, NSubstitute | Презентационные Blazor-компоненты: загрузка, пустота, ошибка, колбэки, локализация, layout | Каждый PR |
| E2E | Playwright .NET | Static SSR вход, SignalR-circuit, быстрый ввод, поиск, представления, drag-and-drop на доске, RU/EN, реальные cookie и статические файлы | Каждый PR |

## Команды

```bash
dotnet test                                       # все наборы
dotnet test TodoList.sln -c Release               # как в CI
dotnet test tests/TodoList.UnitTests
dotnet test tests/TodoList.IntegrationTests
dotnet test tests/TodoList.ComponentTests
dotnet test tests/TodoList.E2ETests
```

Integration- и E2E-тестам нужен Docker. Браузер Playwright ставится один раз после сборки:

```bash
pwsh tests/TodoList.E2ETests/bin/Debug/net10.0/playwright.ps1 install chromium
```

В Linux CI добавьте `--with-deps`, чтобы вместе с Chromium установились системные библиотеки.

## Как запускаются наборы

- Unit-тесты не требуют инфраструктуры.
- Integration-тесты поднимают один контейнер PostgreSQL на коллекцию, и все тесты коллекции используют эту одну базу.
- Component-тесты рендерят компоненты изолированно с сервисами локализации и MudBlazor; база данных им не нужна.
- E2E поднимает контейнер PostgreSQL, запускает реальное веб-приложение на свободном порту, ждёт `/health/ready` и управляет headless Chromium.
- Каждый E2E-сценарий регистрирует своего пользователя и создаёт нужные задачи через `/api/v1`, поэтому сценарии не делят состояние и не зависят от порядка запуска.
- E2E ждёт, пока Blazor навесит обработчики событий, прежде чем кликать, чтобы клик не уходил в нативную отправку формы. Карточки доски, отрисованные после enhanced navigation, маркер `_bl_*` не несут, поэтому тесты доски ждут видимости карточки.
- E2E-контексты используют viewport 1280x800: при стандартном viewport колонки Kanban складываются в столбец, и drag-and-drop между колонками становится нестабильным.

## База данных для integration-тестов

`IntegrationCollection` владеет одним `TodoListAppFixture`: он поднимает один контейнер PostgreSQL, один раз применяет миграции и отдаёт одну и ту же строку подключения всем тестам коллекции. Между тестами база не сбрасывается, а тесты внутри коллекции идут последовательно, поэтому схема создаётся один раз, а не на каждый тест.

Изоляцию дают данные, а не схема:

- Каждый тест создаёт своего пользователя и читает только созданные им строки. Email содержит `Guid`-суффикс, поэтому совпадение имён невозможно.
- Зависимость от порядка тестов считается ошибкой. Тест, которому нужна пустая таблица целиком, чистит её явно: тесты доставки напоминаний отменяют оставшиеся `Pending`-напоминания перед отправкой.
- Основное время уходит на запуск контейнера, поэтому одна общая база и позволяет набору укладываться заметно меньше минуты.

На текущем размере стоимость запуска приемлема. Решение пересматривается, когда выполняется любое из условий:

- Тесту нужен инвариант на всю базу: точное число строк, значение последовательности.
- Тест вынужден удалять чужие данные или начинает зависеть от порядка выполнения.
- Integration-тесты запускаются параллельно либо коллекция растёт настолько, что одна база становится узким местом.
- После падения теста общая база остаётся в состоянии, ломающем следующие тесты.

Меры по возрастанию стоимости: откат транзакции на тест, отдельная схема на тест или сброс в стиле Respawn. Любая из них должна сопровождаться обновлением ADR, а не точечным кодом очистки.

## Test data и fakes

- Общие фикстуры живут в `TodoList.Testing`; типы `[CollectionDefinition]` — в тестовых сборках, которые их используют.
- Unit-тесты Application используют небольшие ручные fake'и, например in-memory `IUserSettingsStore`.
- `TimeProvider` внедряется везде, а тесты доставки напоминаний передают `FakeTimeProvider`, чтобы тайминги back-off были точными, а не зависели от реального времени.
- Отправка email использует fake-реализации `IEmailSender` в integration-тестах.

## CI

- Каждый push и pull request запускает build, unit-, integration-, component- и E2E-тесты.
- CI ставит браузер Chromium для Playwright перед запуском набора.
- Вторая job собирает runtime-образ и образ с bundle миграций.
- Результаты тестов выгружаются артефактом TRX; nightly-запуски пока не настроены.

## Coverage и flakiness

Coverage собирается локально через `coverlet.collector` (`dotnet test --collect:"XPlat Code Coverage"`); в CI он не запускается и gate не является. Цель — 70%+ для Domain и Application, с акцентом на критические пути. Flaky-тест чинится или уходит в quarantine с issue в течение недели.
