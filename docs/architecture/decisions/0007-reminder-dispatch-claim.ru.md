# ADR-0007: Claim для отправки напоминаний

- **Статус:** принято
- **Дата:** 2026-11-14

## Контекст

`ReminderDispatcher` опрашивает outbox `reminders` и отправляет email внутри процесса. Изначальный MVP предполагал одну реплику приложения, потому что `ReminderDeliveryService` выбирал due-строки без claim: две реплики могли прочитать одно и то же `Pending`-напоминание и отправить его дважды.

Приложение должно уметь работать в нескольких репликах без дублей писем, но полноценный claim outbox (статус `Processing`, `FOR UPDATE SKIP LOCKED`, восстановление зависших claim) добавляет схему и логику восстановления, несоразмерные текущему объёму.

## Решение

Сериализуем отправку напоминаний через **session-level advisory lock PostgreSQL**:

- `ReminderDispatchLock` открывает соединение `AppDbContext` и вызывает `pg_try_advisory_lock` со стабильным ключом `0x546F646F4C697374` (`TodoList` в ASCII).
- Dispatcher держит блокировку на один poll. Вторая реплика получает `false` и пропускает poll, не читая due-строки.
- При dispose вызывается `pg_advisory_unlock`; закрытие соединения или падение процесса освобождает блокировку автоматически.
- Блокировка берётся до запроса due-строк, поэтому выборка и отправка происходят внутри критической секции.
- Retention-очистка блокировку не использует: она удаляет только терминальные строки и идемпотентна.

Схема и статусная модель напоминаний не меняются. Ключ блокировки — константа приложения, её нельзя переиспользовать для другой функции.

## Рассмотренные альтернативы

- **`FOR UPDATE SKIP LOCKED` плюс статус `Processing`.** Корректнее и гранулярнее, но требует времени claim, таймаута зависших claim и восстановления после падения реплики посреди отправки. Пока отклонено; это естественный следующий шаг, если объём писем потребует параллельных отправителей.
- **Всегда одна реплика.** Просто, но блокирует масштабирование по причинам, не связанным с circuit Blazor, и оставляет единую точку отказа для отправки напоминаний.
- **Таблица leader election.** Больше движущихся частей, чем встроенный примитив PostgreSQL.

## Последствия

- Несколько реплик приложения могут безопасно запускать dispatcher; за один poll отправляет только одна.
- Blazor Server по-прежнему держит circuit в памяти, поэтому UI требует sticky-сессий до горизонтального масштабирования. Ограничение напоминаний больше не причина держать одну реплику.
- Медленный вызов SMTP держит блокировку на весь batch. Для одного batch-отправителя это приемлемо; держите `Reminders:BatchSize` умеренным, а таймаут SMTP конечным.
- Блокировка привязана к одной базе. Два стека на общей базе сериализуются между собой — это желаемое поведение.
- `pg_locks` показывает advisory lock, поэтому зависший dispatcher диагностируется без логов приложения.
- `ReminderDispatchLock` и dispatcher покрыты интеграционными тестами, которые берут блокировку из двух DI-скоупов, и существующими тестами доставки.
